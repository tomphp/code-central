# Factory scenario tests run on an in-memory fake git held to real git by a contract suite

Status: accepted.

`factory` is the slowest Go package on every OS: 542s on Windows, 276s on macOS and 58s on Linux. Its 500 or so parallel scenario tests start real `git` processes against temporary repositories, 31,071 of them in a full run, 61 per test on average. A test's time follows its git count with a correlation above 0.9 on every OS, and each process costs about 41ms on Windows, 23ms on macOS and 5.5ms on Linux, so git is most of a test's time. Yet most of these tests check the Factory's own rules (the Landing Methods, the CI gate, rebase and replay, Spec branches, Projects with two Repositories, send-backs), not git's behaviour (Spec code-central-1148). So we decided:

- **Every Factory git operation goes through the Git port**, the `git.Git` and `git.Repo` interfaces in `factory/git`. It has two implementations: `git.Real`, which runs git, and `git.Fake`, which keeps every repository in memory.
- **The Fake git keeps real data.** A tree maps paths to file contents, and a commit has a tree, parents, a message and an author. IDs are content-addressed: a 40-hex SHA-1 of a canonical serialization, with no counter or clock, so equal inputs give equal IDs, as git does within the same second. Short IDs are the first 7 characters. One `git.Fake` holds every repository a test uses, keyed by its path.
- **The Fake git merges whole files, three ways.** For `mergeTree` and `replayTree`, per file: when only one side changed the file, or both made the same change, the merge is clean. When both changed it differently and its content is a single line, or absent, on every side, that file conflicts, which is what git does with the rig's one-line fixtures. A file added on both sides, or deleted on one side and changed on the other, counts as both sides changing it.
- **What the Fake git can't model fails the test loudly**, through the `testing.TB` it was made with, and never invents an outcome. That covers a file of several lines changed differently on both sides, a rename meeting a change on the other side, a file on one side where the other has a folder, several merge bases, revision syntax such as `main^`, and any operation it doesn't implement. It fails with `Errorf`, not `FailNow`, because the Factory calls git from its own goroutines, and returns an error too.
- **The Git contract suite**, `gittest.Run`, runs the same cases against `git.Real` on a temporary repository on disk and against `git.Fake`, on every OS on every push, as `storetest.Run` does for the Store. A behaviour the Factory relies on gets a case there before the Fake git models it, so the Fake git can't drift from git.
- **Scripted conflicts go.** The in-package fake repository and its `conflicts` map, which said which merges conflict, are replaced by the Fake git, whose conflicts come from the files.
- **About 16 chosen Real-git tests** keep running real git end to end on every OS on every push, one for each behaviour where git itself matters: each Landing Method, the CI gate, a two-Repository Spec landing, a refused push, a diverged base, a conflict on merge and on replay, worktrees, clones, the git version check and start-up outside a repository. The list may grow towards 25, and not past it without a note in the Ticket that grows it.
- **Every night the whole `factory` package runs on real git** on Linux, macOS and Windows: a "Factory on real git" step in `scale.yml`'s matrix runs `go test -count=1 ./factory/...` with `CODE_CENTRAL_TEST_FACTORY_GIT=real`, so a gap between the Fake git and git shows up within a day.

## Considered Options

- **Real git everywhere**, as before. Rejected: it pays for git's processes on every OS on every push in tests that don't test git, and that cost is the slowest package's time.
- **A higher-level port**, faking the Factory's landing and worktree steps rather than git's operations. Rejected: the Factory's own rules live in those steps, so a fake there would leave the code under test untested and need its own model of every rule.
- **Scripted conflicts**, where a test says which merges conflict. Rejected: a scripted fake answers what the test expects, not what git would do, so a test could pass on a merge git would refuse, and nothing keeps the script in step with git.
- **A line-level diff3 merge in the Fake git.** Rejected: matching git's line merge, hunk boundaries and conflict markers is a project of its own, and the tests don't need it. With one-line fixtures the whole-file rule gives git's outcome, and a case it can't decide fails the test rather than guess.
- **Cutting the process count instead**: caching or batching `rev-parse` and `for-each-ref`, or a long-lived `cat-file --batch`. Rejected for now: `rev-parse` alone is 43% of the processes, but even halving them leaves every test paying for git on Windows and macOS, and caching git's answers risks staleness bugs in the Factory itself. It could be its own Requirement later.

## Consequences

Most Factory scenario tests stop starting git processes, so the package's time falls most on Windows and macOS, once the scenario tests default to the Fake git. A test that writes a multi-line file changed on both sides, or needs an operation the Fake git doesn't model, fails loudly and must use one-line fixtures or run on real git. A new git operation in the Factory needs a contract case, run against both implementations, before the Fake git can model it. Real git still runs end to end on every push in the Real-git tests, and the whole package on real git every night, so a difference between the two is caught within a day rather than on a push.
