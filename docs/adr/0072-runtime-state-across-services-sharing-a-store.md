# Runtime state across services sharing a Store

Status: accepted. Amends [ADR 0008](0008-session-events-are-posted-by-the-factory-and-live-only-in-memory.md) for Heartbeats and pings, which it left in one service's memory beside the Transcripts; adds to [ADR 0068](0068-several-services-may-share-a-postgres-store.md)'s `Services()` side.

ADR 0068 lets several services share a Postgres Store. They hear each other's Changes, but `core` kept its runtime state in the memory of the one service a Factory reported to: each Factory's latest Heartbeat, with its Plan Limits, the Base and clone reports, each session's pings, and the Transcripts and Conversations. So on another service a Factory showed **Offline**, with no Plan Limits, Base or clone reports; a Claim pinging the first service could be flagged Silent; its Transcript was blank, with nothing to say why; and Chat was offered where no Factory would answer it (Spec code-central-1107). So we decided:

- **Heartbeats and pings go on the Store's `Services()` side**, beside Service Registrations and Watcher Leases, read and written outside any View or Update, with the caller's times. There is a Heartbeat row per Factory (Project, Factory name and host) holding the latest Heartbeat whole, its Reporting Service's ID and host and when it expires, a row of Factory reports per Project, a ping row per session, and a Transcript holder row per Claim naming the service its Session Events reach. A new write with the same key replaces the old one, so the newest wins, whichever service it reached. Postgres keeps them as tables made on open with `CREATE TABLE IF NOT EXISTS`; they are not record documents, so they bump no format and need no Migration, and `store move` doesn't carry them. The File Store, SQLite and the fake keep them as they keep Registrations, for the one service holding the Store: in memory, or, on SQLite, in tables cleared when it is opened.
- **`core` writes through and reads from memory.** A Heartbeat, a report, a counted ping and a Claim's first Session Events update the service's memory, as before, then write their row; a Store error there is logged and never fails the call. Reads never hit the database: every service loads the rows into memory on its Factory Status tick, every 10 seconds, and at its start, and the same tick prunes them. Factory Status is still worked out on each read from the Heartbeats, never stored.
- **Transcripts and Conversations stay on the Reporting Service**, in memory, as ADR 0008 has them. The **Reporting Service** is the service a Factory sends its Heartbeats, Session Events and Chat replies to. Another service names its host instead of going blank: "This Transcript is on \<host\>", and Chat says where it runs, the way the Watcher status's `elsewhere` names the Lease holder's.
- **Rows expire.** A Heartbeat row expires 24 hours after its Factory goes Offline, so an Offline Factory stays listed for a day. Ping and Transcript holder rows are pruned after 7 days. Pruning is one idempotent delete any service may run.
- **The Silent Claim floor stays each service's own start.** A service started in the last 30 minutes can lag the others in flagging a Claim Silent, but never flags one falsely.

## Considered Options

- **A contract that a Factory and the UI watching it use the same service.** Rejected: nothing enforces it, a human opening another service's UI sees false Offline and Silent Claims with no hint why, and a Factory that fails over to another service breaks it anyway.
- **Persisting Session Events.** Rejected: ADR 0008's reasons stand. A Transcript is large, fast-moving and worth little once the work is done, and writing every event to the database would make it the busiest table in the Store for the least valuable data.
- **Services proxying reads to each other over HTTP.** Rejected: every service would have to reach every other, across machines and firewalls, with credentials, when today none of them needs to. Naming the host lets the human go there.
- **Moving Conversations into the Store**, or letting a service relay Chat to another. Rejected: a Conversation's turns are taken by a Factory from `next_chat_work` on its Reporting Service, so storing the messages alone would still leave no Factory to answer them elsewhere.
- **Working out Factory Status in the database.** Rejected: the status depends on the reader's clock and the Heartbeat's interval, as it does today, and the database's clock would take the times out of the caller's hands, which the contract suite and `core`'s tests need, as ADR 0068 found for Leases.
- **Publishing a Change notice on every Heartbeat** instead of refreshing on the tick. Rejected: Change notices are for record writes, and every Factory's Heartbeat would wake every Factory and refetch every UI. The tick already bounds Going Offline to 10 seconds, and a Heartbeat seen within one tick is soon enough.

## Consequences

Every service sharing a Store shows the same Factory Status, Plan Limits, Base and clone reports and Silent Claims, within one 10-second tick of each other. A Transcript or a Conversation is still lost when its Reporting Service restarts, and another service names that service's host rather than showing it. Each Heartbeat and counted ping costs one row write, and each tick one read of every row, on any Kind. Every service sharing a Store must run a version with these tables: an older one writes no Heartbeat rows, so its Factories show Offline on the others. On the File Store and SQLite nothing outlives the service, as before.
