# Stores are pluggable, and a database Store keeps document rows

Status: accepted. Partly supersedes [ADR 0003](0003-the-store-is-yaml-files-loaded-into-memory.md), which rejected SQLite; adds to the local settings of [ADR 0056](0056-code-centrals-files-use-the-xdg-layout-on-every-os.md).

ADR 0003 made the store YAML files under one folder, loaded whole into memory, and rejected SQLite because the files would stop being readable and fixable by hand. That stays true of the File Store, and the File Store stays the default: nothing about it changes. But one machine's data folder is not the only place a service can keep its records. A service in a container, or two services sharing one database (Spec code-central-1032), needs a Store that isn't a folder of files. So the service opens one of several **Store Kinds** behind the one `store.Store` interface, chosen by the local settings, and the rest of the service never knows which.

- **The settings choose the Kind.** `settings.yaml` gains a strict `store:` block: `kind` (`files`, `sqlite` or `postgres`, whose Kind is [ADR 0068](0068-several-services-may-share-a-postgres-store.md)'s), `path` (the File Store's folder, or the SQLite database file, defaulting to the data folder and to `code-central.db` in it) and `url_env` (the environment variable a Postgres Store reads its URL from; refused for the other Kinds). An unknown kind, key or value stops `serve`, naming the file and the field, as the port does. No block means a File Store in the data folder, as before. `--store` and `CODE_CENTRAL_STORE` keep their meaning, a File Store at that folder, and override the block, so every existing unit and script runs as it did. The startup line names the Kind and the place (`store: sqlite at /home/me/.local/share/code-central/code-central.db`), never a credential.
- **SQLite is one database file on this machine's disk**, on `modernc.org/sqlite`, pure Go, so the binary stays one static file with no C toolchain. It runs in WAL mode, with an exclusive lock file beside the database (`<db>.lock`), as the File Store has, so a second service refuses to open it by name. It is not for a network share: SQLite's locking doesn't hold there, and neither does the lock file. Its size is the database file plus its WAL.
- **A database Store keeps document rows.** Each record is one row holding the same versioned JSON document the File Store writes as YAML, from the same file structs, decoded by the same strict decoders, so there is one record shape and one format version, in a `meta` row, for every Kind. A Ticket's row keeps its head in one column and each History part (Claims, Rounds, Comments, Moves, Edits, Failure Reports) in its own, so a read with parts loads only those, and the derived head fields (the live Claim, the latest Round) in a column of their own, so a list never loads a History. Beside each document are the indexed columns every query filters or orders on: project, number, state, spec, created, updated and the Link's integration and ID. Side tables hold what a filter looks up by value: labels, tags, pushed commits (repository, commit, branch), blockers, replacements and Claims by session ID. They are written in the record's transaction, from the document, so they can never disagree with it. Usage is a table keyed by Project and day (ADR 0069).
- **One schema, a small dialect.** SQLite and Postgres share the schema and every statement. A dialect names the JSON column type (`TEXT` or `JSONB`), the serial type, and rewrites placeholders; `ON CONFLICT` upserts are the same in both.
- **An Update is one transaction.** `Update` runs its one write in a transaction that is rolled back if the function fails, so a record and its side tables land together or not at all. On SQLite it takes the store-wide lock, as the File Store does; a Shared Store leaves the ordering to the database (ADR 0068).

## Considered Options

- **A sub-package per Kind.** Rejected: the file structs, their strict decoders and the derived-head rules are the record shape, and a Kind that re-declared them would be a second shape to keep in step. Every Kind lives in `store`, and the database ones are left out of the WebAssembly build (`!js`), which only runs the in-memory fake.
- **Columns per field, rather than a document.** Rejected: the record would be declared a third time, in SQL, and every format bump would be a schema migration as well as a file migration. A document row keeps one shape and one migration chain, with indexed columns only for what a query touches.
- **Relaxing a Link's external state on read.** A record with a Link and no external state cannot be read back by any Kind that persists it, and the File Store in memory never noticed. The contract suite's fixtures now write valid Links, the strictness stays, and a database Store decodes each document back before it stores it, so such a record is refused at the write rather than failing every later read.
- **Keeping `--store` as a Kind picker.** Rejected: `--store <dir>` has always meant a File Store at that folder, in every unit `service install` wrote. The block is for what a flag can't say.

## Consequences

`store/storetest`'s contract suite runs against the fake, Files and SQLite in every `make test`, so a Kind can't drift. The service's open step returns an `OpenedStore`, not a `*FileStore`: nothing above `store` can reach a Kind's own methods. `service install` passes `--store` to the unit only when the flag, the variable or no block names a folder; with a block, the service reads it at startup, like the port. A SQLite Store can't be read with `grep` or fixed in an editor; ADR 0003's hand edits are the File Store's, and a human who wants them keeps it. One chain of Migrations serves every Kind: a SQLite Store at an older format is exported, document by document and undecoded, as a File Store layout in a temporary folder, the File Store's chain runs over that, and the result is imported into a new database, swapped in after `VACUUM INTO` has kept the old one as `<db>.format-<n>.bak`. Moving between Kinds and a Postgres Store's Migrations are later Tickets of Spec code-central-1032; the Postgres Kind is ADR 0068.
