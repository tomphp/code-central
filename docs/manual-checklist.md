# Manual checklist for v1

Run this by hand once v1 is built (`make build`). These paths can't be automated in the test suites. Record the date, the version (`code-central --version`) and the result of each step.

## The guides

- [ ] Follow every guide listed in `README.md` on a fresh repository, made as the guide makes it, before a release: the commands, prompts and output still match what the guide shows. Fix the guide in the release if they don't.

## Factory Status

- [ ] With `code-central-factory` running, the Project's dot in the left pane is green and its tooltip (hover, and Tab to focus) lists `code-central-factory on <host>` with `N of M turns running`; Project Options lists the same under **Factories**. Ctrl-C once: the dot turns amber with `draining: …`; once it exits it is grey with `stopped: drained`. `kill -9` the Factory: the dot goes grey within about 100 seconds without a reload. Archived Projects show no dot. The dot reads clearly in light and dark themes.

## `service install`

- [ ] macOS: `code-central service install`; `launchctl print gui/$(id -u)/com.github.tomoram.code-central` shows it running; `curl -sI http://localhost:7733/api/workflow` shows `X-Code-Central-Version`.
- [ ] Log out and back in: the service is running.
- [ ] `kill -9` the service: launchd starts it again.
- [ ] Install through a symlink on PATH: the plist names the symlink, not its target. Replace the target with a new build and run `code-central service restart`: the new version answers.
- [ ] Run `service install` again: the plist is rewritten and the service restarts.
- [ ] Linux: the same steps with `systemctl --user status code-central`, including a re-login and a `kill -9`.
- [ ] Set `port: 7744` in `~/.config/code-central/settings.yaml`, restart, and reach it with `CODE_CENTRAL_URL=http://localhost:7744`. Remove it again.
- [ ] Occupy 7733 with another program: the service refuses to start and names the address.
- [ ] A CLI built from another tag warns once on stderr and still works.

## Upgrading and downgrading

- [ ] Once a release bumps the store `format`: upgrade a real store (`make build`, copy onto `PATH`, `code-central service restart`). The log says `migrated the store from format <n> to <m>`, `code-central.format-<n>.bak` sits next to the store, and agents keep working through the restart.
- [ ] Downgrade by the steps in `docs/running-as-a-service.md`: the old version starts on the `.bak` store, and the old binary refuses the upgraded store with `unknown format`.

## Docker Desktop for Mac

- [ ] From a container, `curl http://host.docker.internal:7733/api/workflow` reaches a service bound only to loopback (unverified assumption in the design).
- [ ] Claude Code inside the container, with `CODE_CENTRAL_URL=http://host.docker.internal:7733`, lists the `code-central` MCP tools.

## Linux Docker with `--bind`

- [ ] `code-central service install --bind 172.17.0.1` (the bridge IP from `ip addr show docker0`); serve prints the LAN warning.
- [ ] A container started with `--add-host=host.docker.internal:host-gateway` reaches `http://host.docker.internal:7733/api/workflow`.
- [ ] The service is not reachable from another machine on the LAN.

## `sbx` (Docker Sandboxes)

- [ ] After `sbx policy allow network localhost:7733`, a sandboxed agent reaches the MCP endpoint (check whether the proxy rewrites `Host`; the allowlist covers both).
- [ ] An older `code-central` copy inside the sandbox warns about the version but keeps working.

## The UI

- [ ] Open the Options view from the Inbox and from Focus Mode, choose **All clear**, and with the Options view open in a second browser, watch it follow the change. Restart the service: the choice is kept, and `options.yaml` sits beside `store.yaml`.
- [ ] Turn **Focus Pop-up** on in the Options view and open the Inbox with something in Needs Me: the **Focus popup** opens over it with the first Focus Item, **Skip**, how many are left and **Open in Inbox**, and the address doesn't change. Close it with ×, then open the Board, Activity, CI and Usage: it stays closed. Have an agent post a Round: it opens again. Choose a Project on the Board: it shows only that Project's Focus Items. Reload on Focus Mode, Options and Project Options with Focus Items waiting: it never opens there. Close it, click in the **Ticket ID** search on **All Tickets** and have an agent post a Round: it waits until you click away. Close it, open a Board card that needs you and have an agent post a Round: it waits until the card's popup closes, then opens for the new Round. Open and close a card's Focus popup with nothing new waiting: it doesn't open. Turn it off: nothing opens on any view.
- [ ] With the installed service and a real `gh`, turn CI Tracking on in Project Options: it saves when `gh` is logged in and can read the repository. After `gh auth logout`, turning it on again (off, then on) is refused with the reason and `gh auth login` as the fix; a repository you can't see is refused naming it. Set the **gh path** Option to a folder without `gh`: the refusal names the Option. Clear it: the Homebrew `gh` is found in its install place even though launchd's `PATH` leaves it out.
- [ ] With the installed service and CI Tracking on, the service log says `started the CI Watcher for <key>` and one `code-central ci-watcher` process runs per such Project. After `code-central service restart` exactly one is running again, and after stopping the service (`launchctl unload`, `systemctl --user stop code-central`, or ending the `Code Central` scheduled task in Task Scheduler) no `ci-watcher` process is left in Activity Monitor, `ps` or Task Manager.
- [ ] With CI Tracking on and Merge + Push to a GitHub repository with an Actions workflow, accept a Ticket: the Factory prints `CI tracks main at …`, and within a minute the Ticket's panel shows a **CI** section with the workflow running, then passed or failed, with its jobs and links that open the run on GitHub. An Ignored workflow's run is greyed and marked ignored.
- [ ] With that Ticket pushed, its row in the Spec view (and in Needs Me or the Activity Dashboard, when it is listed there) shows its CI badge (running, then passed or failed), and the Spec view's sums above its Tickets count it; a Ticket never pushed shows no badge.
- [ ] With CI Tracking on and Merge + Push, let a pushed Ticket's workflow fail: you get one Notification, and its pushed commit shows in Needs Me as **CI failed**, ahead of To merge, one item with no Ticket of its own listing the Ticket. The item's Inbox row opens the Ticket, and its panel and its Focus Item show the item's Tickets and the CI section with **Land anyway**; choosing it takes the item out of Needs Me, and the Factory prints `landing anyway at …` and lands it on its next poll. Under Branch + Push the panel offers no Land anyway.
- [ ] With two Accepted Tickets on different Specs pushed and the base's tip failing (merge the second while the first still waits on CI), Needs Me has one **CI failed** item listing both, with one Notification; each Ticket's view shows CI failed and names the other; Send back to fix isn't offered; **Land anyway** on the item lands both, and `project.yaml` holds the response once, under `ci_responses`. When a later commit containing their work passes instead, the item leaves Needs Me and neither Ticket gets a comment.
- [ ] With a pushed Ticket CI failed, under Merge + Push and again under Branch + Push, choose **Re-run failed jobs** on its item's panel or Focus Item: the item leaves Needs Me with the Ticket's CI result running, the run's failed jobs re-run on GitHub as a new attempt, and the CI view and the Ticket's CI section show that attempt; once it passes, the Ticket's CI result is passed.
- [ ] With a pushed Ticket's workflow cancelled on GitHub, its pushed commit shows in Needs Me as **CI cancelled**, one item listing the Ticket, with no CI-failed Notification, offering Re-run, Land anyway (Merge + Push only) and Send back to fix but no New fix Ticket; nothing re-runs by itself. The cancelled run, the CI result, the CI badge and the Needs Me row show in neutral grey labelled **cancelled**, not the red of a failed run. Choose **Re-run**: the cancelled run runs again, and once it passes the Ticket's CI result is passed and it lands.
- [ ] On a CI failed item listing one Ticket, the failure options' note is prefilled with the failed run's link, its failed jobs and the `gh run view` command. **Send back to fix** moves it to Ready with the note; the Factory claims it again in its existing worktree, and its re-accept reports a new pushed commit whose CI result decides. **New fix Ticket** opens a Ready Ticket on the Project's CI Fixes Spec with the note; the failed Ticket stays Accepted, the item leaves Needs Me, and when the fix's push passes CI the Factory lands it. Cancelling the fix Ticket while the commit still fails brings the item back. Both are offered under Branch + Push too.
- [ ] With the installed service and an Azure DevOps project, set the CI Provider to **Azure Pipelines** in Project Options, with the project URL (also try a `.visualstudio.com` URL and one pasted with `/_build`). With `ADO_PAT` unset, turning CI Tracking on is refused naming `ADO_PAT` and the OS's way to set it for the service. Set it with a PAT that has only an unrelated scope (not Build: Read): the refusal says the PAT needs Build: Read & execute. Set it to a revoked PAT: refused as rejected. A project URL for a project you can't see is refused on the URL field. Set it to a PAT with Build: Read & execute, then `code-central service restart`: it saves, and the watcher shows **Watching <project URL>**. A Push remote on Azure Repos prefills the URL, with a note.
- [ ] With CI Tracking on for Azure Pipelines and Merge + Push to Azure Repos with a pipeline, accept a Ticket: the Ticket's **CI** section shows the pipeline's run (named by its pipeline name, with the build number) running, then passed, with its jobs (no stages or tasks) and **View on Azure DevOps** links that open the build. Make a pipeline fail: the Ticket is **CI failed**, with the failed jobs. Make one finish **partially succeeded** (a job with `continueOnError`): the run shows **Partially succeeded** with a warning mark, and the Ticket's CI result is passed and it lands.
- [ ] With an Azure Pipelines Ticket CI failed, choose **Re-run failed jobs**: Azure DevOps retries the build's failed jobs as a new attempt of the same build, and the CI view and the Ticket's CI section show that attempt. With a PAT lacking the execute scope, the Re-run request shows as refused.
- [ ] With an Azure Pipelines Project, add a CI Rule for a pipeline name (spaces allowed) on `main`, and push to `main` outside the Factory: when the pipeline fails, the rule fires and opens a Fix Ticket naming the failed jobs. An Ignored workflow naming a pipeline greys its run and keeps it out of the CI result.
- [ ] With CI Tracking on and a workflow running, open **CI** in the Inbox's Admin section: the CI Watcher shows Watching, the run is listed first with its duration counting up, and when it finishes its row pulses and moves below any still running. **View on GitHub** opens the run, and its Ticket link opens the Ticket.
- [ ] With GitHub Issues on and New issues need me on, a new Incoming Issue shows in Needs Me under **New issue**, its row reading `github owner/repo#n came in …`, and as a Focus Item with its panel; the New issue dot and label read clearly in light and dark themes. **Keep as Draft** takes it out of Needs Me and moves Focus Mode on, and its Ticket panel still offers Keep as Draft in its **Triage** section. On GitHub, the issue gets the `code-central:draft` label, created in the repository if it was missing.
- [ ] On an Incoming Issue, choose **To Requirement…**, type some context and confirm **To Requirement**: the Ticket is Cancelled with the grilling Stage as its Replacement and leaves Needs Me, and the new Requirement's text is the issue's title, its description and the context, with a **github owner/repo#n (outbound)** badge and **Open in GitHub**. Within a check the issue on GitHub gets one comment with the context and a link back to the Requirement, and the `code-central:requirement` label in place of `code-central:draft`. Editing the issue on GitHub changes nothing in Code Central, and restarting the service posts nothing more.
- [ ] On an Incoming Issue, choose **Won't fix…**, type a reason and confirm **Won't fix**: the Ticket is Cancelled with the reason as its comment and leaves Needs Me, and within a check the issue on GitHub gets one comment with the reason and a link back to the Ticket, the `code-central:wont-fix` label in place of `code-central:draft`, and is closed as not planned. Restarting the service posts nothing more.
- [ ] Let a Requirement made from an issue run through the Factory: within a check of each step, the issue on GitHub gets one comment with the grilling's resolution (not the finish summary), one with the Requirement's text as the spec Stage left it, and one per implementation Ticket as it lands, with its commit; its label moves from `code-central:requirement` to `code-central:building` once the Stages are Done. Once the last Ticket lands, the issue gets the list of what landed, `code-central:done`, and is closed as completed. Restarting the service posts nothing more.
- [ ] On a fresh store, with Focus Mode open in a second browser, it shows the Activity Dashboard. Choose **All clear** in the first: Focus Mode switches from the dashboard to All clear without a reload, and choosing **Activity Dashboard** again switches it back. The dashboard's Ready and In Progress counts match the Inbox's State views with their folded Stage Tickets added, and while a real Session runs, its entry's latest event line keeps up. When something needs you, the dashboard gives way to the Focus Item.
- [ ] With a Project chosen in the Inbox and a Ticket waiting on you in Needs Me, click **Activity** in the Admin section, between **Usage** and **CI**: the dashboard shows on that Project, not Focus Mode's Focus Item, whatever Option you chose for when nothing needs you. The **Projects** picker switches it to another Project or All Projects and the address follows; clicking an In Progress entry opens its Ticket in the Inbox; **Back to the Inbox** returns to the Inbox as you left it. With CI Tracking on, its **CI Running** block opens the CI view, and **Back to Activity** returns to the same Project.
- [ ] With CI Tracking on in a Project, the Activity Dashboard shows a teal **CI Running** block after Ready and In Progress; with none on, or Focus Mode filtered to a Project with it off, there is no such block. While a pushed Ticket's workflow runs, the block counts its run (but not a run of an Ignored workflow or a CI Rule's), pulses as runs start and finish, and reads 0 once they're done. Clicking it opens the CI view on Focus Mode's Project, and **Back to Focus Mode** returns. Below the In Progress list, the **CI Running** list shows each counted run with its workflow, Ticket ID, branch, short commit and how long it has been running, or "No CI Runs running"; clicking an entry opens its Ticket in the Inbox, and its **View on GitHub** link opens the run on GitHub in a new tab.
- [ ] With the dashboard showing, while a real Session runs, its entry pulses (a short scale-and-glow) as its events arrive, at most about every 5 seconds, and a count block pulses only when its number changes. A Ticket that is claimed while you watch joins the list with one pulse. With the system's reduce-motion setting on, the pulse is a brief brightness flash with no scaling.
- [ ] Open a Map with a few Tickets and Blockers in a narrow and a wide window, in light and dark themes: the graph reads left to right with arrows from each Blocker, every node's type, title and State fit, the progress colours read clearly, the fog node sits dim at the right edge, and the graph scrolls sideways rather than squashing when the pane is narrow. **Decisions so far** and **Out of scope** sit beside the graph, or under it when there's no room.
- [ ] On a spec Stage In Review, the review panel offers **Split into Tickets** and **Implement**. The agent's finish recommended one of them: that button is highlighted and marked *Recommended*, and the finish summary ends with a one-line reason. Choose **Implement**: the spec Stage is accepted, one implementation Ticket is Ready on the Spec, the tickets Stage is Cancelled, and the Requirement's strip shows its Tickets segment as skipped (not done) with Build at *0/1*. The Factory claims the implementation Ticket without a tickets Stage. On another Requirement, **Split into Tickets** runs the tickets Stage as usual.
- [ ] On a Requirement, a Map and a plain Spec (opened from its name in the Ticket panel), in light and dark themes: **New Prototype** sits under the title, its dialog submits, and the new Prototype opens in the Ticket panel.
- [ ] On a Draft Ticket, in light and dark themes, choose **Edit** in its panel: the title becomes an input and the description a textarea. Change both, toggle **Preview** (the Markdown renders as the panel shows it, and toggling back keeps your text), then **Save**: the panel shows the new text and its History reads "title and description edited by human", with **show previous** giving the old text. An empty title is refused with the reason and the form stays open.
- [ ] Open a Requirement's view: its **Requirement's text** section is closed, opens on click, and its **Edit** changes the title and text; once the spec Stage is Done the section is headed **Spec**. On a plain Spec, **Body** works the same way. A Spec with no Tickets can be edited.
- [ ] In light and dark themes, open a State list in the Inbox (Ready, say): a **By Ticket | By Spec** control sits at the top, By Ticket pressed, the list as before; Needs Me and Requirements have no control. Choose **By Spec**: the address gains `group=spec`, and the list is one collapsed Spec row per Spec with Tickets in that State, in the order of the flat list. Each row's first line is a chevron, the ID, a kind badge (Map, Spec or Long-lived; none on a Requirement), the title and the needs-you dot; then a Requirement's Stage strip, or a chip per State any other Spec has Tickets in, this State filled and the others tinted; then the headline, with "n of m" when the list holds only some of the Spec's Tickets. A plain Spec's headline is its first need (say "Failed"), else "A Factory is on it" while one of its Tickets is claimed, then "d of t Done"; a Map's is its decision count. A row with a Ticket that needs you has the dot and an amber edge. The chevron opens a row to its Tickets as two-line rows without leaving the list; a Requirement's Stage Tickets sit in its row with their Stage shown, and there is no Stage Tickets group. Select a Ticket: its row opens on its own and can still be closed. Click a row anywhere but the chevron: the Spec opens on the right, its row marked current. The grouping survives switching State lists, Needs Me, Projects and a reload. The choice is kept per browser: a bare address in the same browser opens By Spec, while another browser opens By Ticket.
- [ ] In the Requirements view and Needs Me's Requirement groups, every Requirement and Map is the same Spec row: a Map shows its State chips and its decision count (`3/7 decided · 1 needs you`), a Requirement its Stage strip and headline. The chevron opens a row on all of the Spec's Tickets, Stage Tickets first, each with its State chip; a click elsewhere opens the Spec. Finished Requirements and those with nothing needing you stay dimmed in the Requirements view.
- [ ] **All Tickets**: in the sidebar's View links, **All Tickets** sits with its count, the Tickets that are neither Done nor Cancelled, and follows the Project filter. Open it: every Ticket of every kind and Stage is listed newest first by creation, each row with its State chip, needs-you dot, kind label and its Spec. The **By Ticket | By Spec** control works here too: By Spec shows one Spec row per Spec, expanding to its Tickets, and the grouping survives a reload. Done and Cancelled Tickets are hidden until **Show finished** is ticked (`finished=1` in the address, kept per browser); Accepted Tickets show either way. Type part of an ID in the **Ticket ID** search box (`12`, `#12`, or a Spec's ID): only matching Tickets (or Tickets of a matching Spec) show, even finished ones, and clearing the box restores the list. With nothing matching, an empty message shows.
- [ ] **Board link**: with a Project chosen in the Inbox, **Board** is the last View link, after **All Tickets** and its States, and its count matches **All Tickets**. Click it: the Board opens on that Project with **Board** as its title and the **Projects** picker on it; switching the picker to All Projects updates the address. **Back to the Inbox** returns to the Inbox as you left it.
- [ ] **Board columns**: the columns read Draft to Accepted, left to right, each head with its count and a coloured bar; Done and Cancelled are hidden and **Columns ▾** reads `Columns · 8/10 ▾`. An empty column reads "No Tickets". At 1440px wide the eight columns fit without sideways scrolling; narrow the window and the Board scrolls sideways, with the column heads staying at the top as you scroll down. In **Columns ▾**, tick Done and Cancelled: the button reads `Columns ▾` and the address has `hide=`. Reload, then open the Board again from the Inbox: every column still shows, and the Board link's count now includes Done and Cancelled Tickets. Open an address with `hide=Draft`: only Draft is hidden, whatever you chose before.
- [ ] **Board cards**: each card shows its ID, kind label, a CI badge for a not-Done Ticket with a CI result (none on a Done card, even with Done shown in Columns ▾; it changes as the CI result does), **⛔ Blocked** for a Ticket with open Blockers and the needs-you dot, its title (up to 3 lines) and its Spec's kind and name; a card that needs you has a coloured left border. Cards are newest first in each column. Move a Ticket to another State from an agent: its card moves column without a reload and glows twice; nothing glows when the Board first opens. Dragging a card does nothing.
- [ ] **Opening a card**: click a card on the Board: its **Ticket popup** opens over the Board with the Ticket's pane, and the address gains `popup=<id>`. Close it with ×, then reopen and close it with Escape, a click outside it and the browser's Back in turn: each time the Board stays with the same Project, columns, grouping and folded lanes, and focus is back on the card. Reload with the popup open: it reopens. Cmd-click (or middle-click) a card: the Board opens in a new tab with its popup. Have an agent post a Round of two Questions on a Ticket, then click its card: its **Focus popup** opens with Question 1 of 2 and no Skip, count or Open in Inbox. Answer both: the popup moves on to the Ticket's **Answered** item, and once the agent picks the answers up it closes by itself, back on the Board. Pick **Spec** on the Board's toggle, then open a State list in the Inbox: it is By Spec too. Submit a Small Change from the Board's **+ New ▾**: its Ticket opens in the Inbox.
- [ ] **Board By Spec lanes**: on the Board, pick **Spec** on the **Ticket | Spec** toggle: the columns split into one lane per Spec that has a Ticket in a shown column, newest Spec first, each headed by its Lane header as a one-line bar across the Board (title, headline and "N shown", no Stage strip), and the address has `group=spec`. Cards in a lane have no Spec line, and each column head's count is the total across lanes. Scroll sideways: the Lane headers stay pinned at the left. Click a Lane header (not its chevron): the Spec's popup opens over the Board with the Spec's pane (Requirement, Map or Spec) and the address gains `popup=<Spec ID>`; click a Ticket in it and the popup switches to that Ticket's popup, and Back returns to the Spec popup; Escape closes it and the grouping, hidden columns and folded lanes are as they were. Click a lane's chevron: the lane folds to its header with a count under each column, the column heads' counts don't change, and clicking it again unfolds the lane; reloading unfolds every lane. Pick **Ticket**: the columns show alone, and the Inbox's State lists follow the same pick.
- [ ] **Short IDs**: with one Project selected, Ticket and Spec IDs in the lists, rows and headers show as `#123`; hover shows the full ID. With All Projects selected the full ID (`acme-shop-123`) shows instead. Click either: the full ID is copied and the text reads "Copied" for a moment.

- [ ] With a Map's Ticket and a Prototype in Needs Me, in light and dark themes: each is its own row with `↳ Map: …` (or the plain Spec's title), and the **Prototype** badge reads clearly beside the title, in the row and on its Focus Item.
- [ ] In Focus Mode, with a few items skipped, submit a Requirement, a Map and a Small Change from **+ New ▾** in the header: the Focus Item stays, the skipped list is kept, a "Requirement added", "Map added" or "Small Change added" note shows under the header and goes after about 4 seconds, and with Focus Mode filtered to a Project, the dialog preselects it. Submitting a Small Change from the sidebar opens its new Ticket, Ready, on the Small Changes Spec. The ▾ menu's keyboard behaviour works as in the sidebar, over its three items (↓ opens on the first item, ↑ and ↓ wrap, Esc returns to ▾, Tab closes), and in light and dark themes the button looks plain beside **Exit**.

## Real Claude Code

- [ ] `code-central init` in a repository; a new session lists the `code-central` MCP server.
- [ ] The PreToolUse hook `code-central hook session-id` adds `session_id` and `client_version` to `claim`, `set_session` and `post_round` (and `working_dir` to `claim` and `set_session`) through `updatedInput`, and the normal permission prompt still appears.
- [ ] `CLAUDE_CODE_SESSION_ID` is set in the session's Bash tool and matches the hook's `session_id`.
- [ ] The PostToolUse hook `code-central ping` keeps a Claim from turning Silent, and never slows or blocks a tool call, even with the service stopped.
- [ ] `code-central service restart` while a session is mid-`wait`: `wait` resumes, and the MCP server reconnects without the session marking it failed.
