# Several services may share a Postgres Store

Status: accepted. Adds the Postgres Kind to [ADR 0067](0067-stores-are-pluggable-and-a-database-store-keeps-document-rows.md); partly supersedes [ADR 0002](0002-the-service-is-the-only-writer.md), for a Postgres Store: several services write it, and the database, not one process, orders their writes.

ADR 0067 made the Store pluggable and gave the database Kinds one schema of document rows. SQLite is one machine's file: one service holds it, under a lock file, and its `Update` takes the process-wide lock, as the File Store's does. A **Postgres Store** (Spec code-central-1032) is the Kind several services, on several machines, open at once: nothing can hold a process-wide lock for all of them, and a lock file on one machine means nothing to another. So the Postgres Kind is the first **Shared Store**, and the database, not the service, orders its writes.

- **Postgres on pgx, the same schema, JSONB documents.** The Kind runs on `github.com/jackc/pgx/v5` through `database/sql`, so the readers, writers and Usage are the SQLite ones under a dialect that numbers the placeholders, names the document column `JSONB` and the serial `BIGSERIAL`. The schema is created on first open, under a transaction-level advisory lock, so two services opening a fresh database create it in turn and the second finds it made. The format check is ADR 0067's, and a Postgres Store at an older format is migrated in one transaction (below).
- **No lock, and no process-wide mutex.** A Postgres Store takes no lock file: a second service is the point. `Update` runs each attempt in a `SERIALIZABLE` transaction and `View` in a `REPEATABLE READ READ ONLY` one, so every read in a View sees one moment, and no View blocks an Update or is blocked by one.
- **Change notices go over `LISTEN` and `NOTIFY`.** `Announce` is a `pg_notify` inside the Update's transaction, so Postgres sends it only when the Update commits, and a retried attempt's notice dies with its rollback. Its payload is the Change as JSON, with the ID of the Store handle that sent it. The channel is one per schema (`code_central_` and the schema name's MD5), since a channel belongs to the whole database and two Stores in one database must not hear each other. `Changes` keeps one connection of its own, named `code-central changes <service ID>` among the database's connections, listening on the channel; it is made before `Changes` returns, so nothing committed after that is missed, and it leaves out the handle's own notices. A connection that fails, or doesn't answer a ping after 30 s without a notice, is made again with a backoff that doubles from 100 ms to 10 s. The notices sent while it was down are lost, so once it listens again it delivers one `project.changed` per Project, which wakes the Factories: `wait` and the UI refetch, and `next_factory_wake` returns, so no waiter is left behind.
- **Each service registers itself.** A running service writes its **Service Registration**, a row holding its ID (new each start), host, version and format, and when it last renewed it. It renews it every 10 seconds, and it counts as live for 30, so a service that misses two renewals in a row keeps its place; a clean shutdown deletes it, once the service's Watchers have stopped. A service that died without deregistering stops counting 30 seconds after its last renewal. The Store interface carries this as `Services()`, read and written outside any View or Update; the File Store and the fake keep it in memory, where the one service is the only one registered, and a SQLite Store clears its rows when it is opened, since its lock means no other service is running.
- **A Project's Watchers run on the one service holding its Watcher Lease.** The **Watcher Lease** is a row per Project naming the holding service and when it expires, 30 seconds after its last renewal. The service's Watcher supervisor renews every Lease it holds, and tries to take each other one, as the Project is first watched and every 10 seconds; it takes one only if it is free or expired, in one `INSERT … ON CONFLICT DO UPDATE … WHERE` statement, so two services trying at once can't both win. It runs a Project's Watchers only while it holds the Lease, and stops them once another service has it. A service that deregisters lets go of its Leases at once, so another takes them on its next tick. The Project's Watcher status, in `get_project` and the UI, names the host holding the Lease: the service's own Watcher's status while it holds it, `elsewhere` with the host while another does (its Watcher's status shows there), and `waiting`, "Waiting for a service to take the Watchers.", once it has lapsed with no live service to take it. The times are each service's own clock's, so a test runs them on a fake clock; the hosts' clocks must agree to within a few seconds, as NTP keeps them.
- **The format gates a service at its start and on every renewal.** A service refuses to start on a Store at a newer format than its own, by name, as before. A running one reads the Store's format each time it renews its Registration: one another service has migrated past its own is a `store.FormatChangedError`, naming both formats, on which `serve` stops and exits with that message. Between renewals, every Update on a Shared Store reads the format first, in its own transaction, and is refused the same way, so an old service never writes a record of a format it doesn't know.
- **A Postgres Migration runs in one transaction, with no other service registered.** The Store is staged as a File Store layout in a temporary folder, by the exporter Store Move uses, the File Store's chain of steps runs over it, as for every Kind, and the record tables are dropped, made again in this build's layout and loaded with the result, all in one transaction. It takes the schema's advisory lock first, so a service opening the Store meanwhile waits and then finds it migrated, and then the Registrations table in `SHARE` mode, so no service registers or renews until it commits. It refuses, naming each one by host and version, while any other live Registration exists, and leaves the Store untouched; a service that stopped without deregistering stops counting after 30 seconds. It keeps no copy aside: the transaction commits whole or not at all, so the database, and any backup or point in time of it, is at one format or the other.
- **A colliding Update is tried again, then fails with `ErrConflict`.** When Postgres can't order two services' transactions (SQLSTATE `40001`), or they deadlock (`40P01`), the loser's attempt is rolled back whole and its function is run again from the start, so it reads what the winner wrote: a Claim finds the Ticket claimed, a create finds its number taken. It gets five attempts, with a jittered backoff that doubles from about ten milliseconds, and then `Update` fails with `ErrConflict`, which the doors answer as a 409 `conflict`: "another service changed this at the same moment, so nothing was written; try again". An Update's function must therefore be safe to run more than once, which `store.Store`'s contract already asks.
- **The URL is the environment's, and the Location never shows it.** The `store:` block names the Kind and `url_env`, the environment variable the service reads the URL from, `CODE_CENTRAL_DATABASE_URL` by default; the settings file never holds a credential. `store.PostgresLocation` keeps the URL in an unexported field for `OpenAt` alone, and everything printed (the startup line, the log, an error) shows `postgres at host:port/database`. A bad URL is reported with pgx's message, which masks the password.
- **The contract suite runs on Postgres in CI, each test in a schema of its own.** `CODE_CENTRAL_TEST_POSTGRES_URL` names a database the tests may fill and empty; CI runs one as a service container, in a Linux job of its own, since no other runner can give one. Each test creates a schema, opens the Store with `search_path` set to it and drops it after, so tests run in parallel and leave nothing. Without the variable the Postgres cases skip, naming it, so `make test` needs no Postgres. The Shared Store cases, two services' Updates at the same moment, run on any Kind whose factory gives a second handle: one Claim wins, two creates take different numbers (two Tickets, and a Spec beside a Ticket, which collide on no key), and an Update that keeps colliding fails with `ErrConflict` after five attempts.

## Considered Options

- **A version column and an optimistic check.** Rejected: every record and every side table would carry a version, every write would compare it, and a read-then-write across two records (a Claim reads the Ticket and the Project's Watchers) would still need the engine's help. Serializable snapshot isolation gives the check for every row an Update read, without a column.
- **An advisory lock around every Update.** Rejected: it serializes every write of every service through one lock, across machines, and gains nothing a serializable transaction doesn't, since nearly all Updates touch different records.
- **`READ COMMITTED` Updates.** Rejected: a check and the write it guards would no longer be atomic between services. Two Claims would both read an unclaimed Ticket and both write a Claim; the second would overwrite the first.
- **Retrying for ever.** Rejected: a record two services fight over would hold a caller for ever. Five attempts cover the collisions a workflow produces, and `ErrConflict` tells the caller what happened and that trying again is right.
- **One transaction per View, as `SERIALIZABLE`.** Rejected: a serializable read-only transaction takes part in the engine's conflict detection, so a long View could abort an Update. `REPEATABLE READ` gives the View its one snapshot and leaves the Updates alone.
- **One leader service running every Project's Watchers.** Rejected: the leader would carry every Watcher, and losing it would stop them all at once. A Lease per Project spreads them over the services that are running, and a lapsed one is taken Project by Project.
- **A Lease per Watcher, not per Project.** Rejected: a Project's Watchers report through the same service and share its tools and credentials (gh, the Azure DevOps PAT), so splitting them across hosts would make a Project's status depend on several machines' setup at once.
- **The database's clock for Registrations and Leases.** Rejected for now: it would spare the hosts agreeing on the time, but the Store interface would no longer take its times from the caller, so the contract suite and core's tests couldn't run them on a fake clock. Hosts kept by NTP agree far closer than the 30 seconds a Lease lives.
- **Migrating with other services still running, then telling them.** Rejected: a service at the old format would go on writing records of that format into the new one between the Migration and its next renewal. Refusing while another is registered, and stopping a running one whose format the Store has passed, keeps every write at the Store's format.
- **Copying the old tables aside before a Migration, as SQLite copies its file.** Rejected: one transaction already leaves the Store at the old format if anything fails, and a copy inside the same database would double its size and outlive its use; the provider's backups and point-in-time recovery are the backup.
- **Polling the Store for what changed.** Rejected: every service would read every Project's latest update over and over, and a waiter would still lag by the polling interval. `NOTIFY` costs nothing between writes, and is sent only on commit, which is what a waiter needs.

## Consequences

The contract suite runs against the fake, Files, SQLite and, in CI, Postgres, so no Kind drifts, and the Shared Store cases keep a Shared Store honest about collisions. `core` already answers `ErrConflict` as a 409 that asks the caller to try again; the UI and agents see it only when two services change one record at the same moment. A Postgres Store is backed up with Postgres's tools, and a Migration runs as one transaction, so a backup is one format or the other. Upgrading the services sharing a Store means stopping them all, starting one at the new version, which migrates it, and then the others: an old one started after refuses the Store, and one left running exits at its next renewal. Several services share a Project's Watchers through its Lease, so each Project's run once, on the host its status names; a service that dies without deregistering holds its Leases for up to 30 seconds, and its Projects' Watchers stop meanwhile. Several services sharing a Postgres Store hear each other's changes: a write on one machine ends a `wait`, wakes `next_factory_wake` and refreshes the UI on the others.

Added to by [ADR 0072](0072-runtime-state-across-services-sharing-a-store.md): the `Services()` side also keeps the Heartbeats, Factory reports, pings and Transcript holders, so the services sharing a Store show the same Factory Status and Silent Claims.
