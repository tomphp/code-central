# Several services may share a Postgres Store

Status: accepted. Adds the Postgres Kind to [ADR 0067](0067-stores-are-pluggable-and-a-database-store-keeps-document-rows.md); partly supersedes [ADR 0002](0002-the-service-is-the-only-writer.md), for a Postgres Store: several services write it, and the database, not one process, orders their writes.

ADR 0067 made the Store pluggable and gave the database Kinds one schema of document rows. SQLite is one machine's file: one service holds it, under a lock file, and its `Update` takes the process-wide lock, as the File Store's does. A **Postgres Store** (Spec code-central-1032) is the Kind several services, on several machines, open at once: nothing can hold a process-wide lock for all of them, and a lock file on one machine means nothing to another. So the Postgres Kind is the first **Shared Store**, and the database, not the service, orders its writes.

- **Postgres on pgx, the same schema, JSONB documents.** The Kind runs on `github.com/jackc/pgx/v5` through `database/sql`, so the readers, writers and Usage are the SQLite ones under a dialect that numbers the placeholders, names the document column `JSONB` and the serial `BIGSERIAL`. The schema is created on first open, under a transaction-level advisory lock, so two services opening a fresh database create it in turn and the second finds it made. The format check is ADR 0067's: a database at another format is refused by name.
- **No lock, and no process-wide mutex.** A Postgres Store takes no lock file: a second service is the point. `Update` runs each attempt in a `SERIALIZABLE` transaction and `View` in a `REPEATABLE READ READ ONLY` one, so every read in a View sees one moment, and no View blocks an Update or is blocked by one. The service's place in a Shared Store, its Registration and the Watcher Leases, are a later Ticket (code-central-1049), as are the change notices between services (code-central-1048): until then, `Changes` delivers nothing and `Announce` is ignored, as for the other Kinds.
- **A colliding Update is tried again, then fails with `ErrConflict`.** When Postgres can't order two services' transactions (SQLSTATE `40001`), or they deadlock (`40P01`), the loser's attempt is rolled back whole and its function is run again from the start, so it reads what the winner wrote: a Claim finds the Ticket claimed, a create finds its number taken. It gets five attempts, with a jittered backoff that doubles from about ten milliseconds, and then `Update` fails with `ErrConflict`, which the doors answer as a 409 `conflict`: "another service changed this at the same moment, so nothing was written; try again". An Update's function must therefore be safe to run more than once, which `store.Store`'s contract already asks.
- **The URL is the environment's, and the Location never shows it.** The `store:` block names the Kind and `url_env`, the environment variable the service reads the URL from, `CODE_CENTRAL_DATABASE_URL` by default; the settings file never holds a credential. `store.PostgresLocation` keeps the URL in an unexported field for `OpenAt` alone, and everything printed (the startup line, the log, an error) shows `postgres at host:port/database`. A bad URL is reported with pgx's message, which masks the password.
- **The contract suite runs on Postgres in CI, each test in a schema of its own.** `CODE_CENTRAL_TEST_POSTGRES_URL` names a database the tests may fill and empty; CI runs one as a service container, in a Linux job of its own, since no other runner can give one. Each test creates a schema, opens the Store with `search_path` set to it and drops it after, so tests run in parallel and leave nothing. Without the variable the Postgres cases skip, naming it, so `make test` needs no Postgres. The shared-Store cases, two services' Updates at the same moment, run on any Kind whose factory gives a second handle: one Claim wins, two creates take different numbers, and an Update that keeps colliding fails with `ErrConflict` after five attempts.

## Considered Options

- **A version column and an optimistic check.** Rejected: every record and every side table would carry a version, every write would compare it, and a read-then-write across two records (a Claim reads the Ticket and the Project's Watchers) would still need the engine's help. Serializable snapshot isolation gives the check for every row an Update read, without a column.
- **An advisory lock around every Update.** Rejected: it serializes every write of every service through one lock, across machines, and gains nothing a serializable transaction doesn't, since nearly all Updates touch different records.
- **`READ COMMITTED` Updates.** Rejected: a check and the write it guards would no longer be atomic between services. Two Claims would both read an unclaimed Ticket and both write a Claim; the second would overwrite the first.
- **Retrying for ever.** Rejected: a record two services fight over would hold a caller for ever. Five attempts cover the collisions a workflow produces, and `ErrConflict` tells the caller what happened and that trying again is right.
- **One transaction per View, as `SERIALIZABLE`.** Rejected: a serializable read-only transaction takes part in the engine's conflict detection, so a long View could abort an Update. `REPEATABLE READ` gives the View its one snapshot and leaves the Updates alone.

## Consequences

The contract suite runs against the fake, Files, SQLite and, in CI, Postgres, so no Kind drifts, and the shared-Store cases keep a Shared Store honest about collisions. `core` already answers `ErrConflict` as a 409 that asks the caller to try again; the UI and agents see it only when two services change one record at the same moment. A Postgres Store is backed up with Postgres's tools, and a format migration, when it comes (Ticket code-central-1049; until then a Postgres Store at an older format is refused by name), runs as one transaction, so a backup is one format or the other. Until code-central-1048 and code-central-1049, several services sharing a Postgres Store write safely but don't hear each other's changes and don't share their Watchers.
