# get_ticket leaves out Rounds, moves and edits by default

`get_ticket` returned the whole Ticket: every Round with every Question, every comment, the full list of moves, edits and past Claims. A Ticket that went through grilling came to about 20KB (code-central-165 was 19.8KB, 180 was 24.0KB), most of it Rounds (9–11KB) and comments (7–11KB), and `claim` returned the same whole Ticket again. We decided that a read naming no `parts` returns the Ticket's other fields (description, State, Spec, Blockers, branch and commit, …) with three parts: `claims`, `failure_reports` and `comments`. It leaves out `rounds`, `moves` and `edits`, and a `left_out` field counts each part it left out that has anything, such as `{"rounds": 2, "moves": 8}`, so an agent sees there is more instead of taking a missing part for an empty one. `parts` names exactly the parts a read returns, as `get_spec`'s does, out of `claims`, `failure_reports`, `comments`, `rounds`, `moves` and `edits`; naming all six is the whole Ticket. `claim` returns its Ticket in the same default shape, so most Claims need no `get_ticket` at all.

Every comment stays in the default because comments carry what a redo needs: rejection, give-up, send-back and merge-conflict notes, the earlier Claim's finish summary and the grilling resolution comment. Claims are small and say how each one ended, and Failure Reports are why a Ticket failed. Rounds are the human's verbatim answers, which only two readers need: a grilling redo, whose earlier answers stand, and the spec Stage, which works from the grilling Ticket's resolution and reads a Round when the resolution points to one. Their Stage Guides tell them when to ask for `rounds`. Moves only retell the timeline that claims, Failure Reports and comments already explain, and edits hold previous titles and descriptions.

## Considered Options

- **Only the latest comments, or those since the previous Claim.** Rejected: cutting comments risks dropping the rejection or note a redo has to answer, and a cut that makes an agent miss information is a regression. Comment-heavy Tickets (code-central-186, 23KB) shrink only about 20% as a result; long finish summaries are cut separately.
- **The smaller default only at the MCP door.** Rejected: MCP and the CLI are both agent doors and would disagree. The default lives in core, and the CLI's `get-ticket` reads it too.

## Consequences

The HTTP API keeps returning the whole Ticket when no `part` is named, because the web UI and the Factory read every part (the Factory reads moves to time landings); the client's `GetTicket` with no parts is that whole Ticket, and the CLI names the default parts itself. A write with `full` still returns the whole Ticket. The workflow's step 2 and the Stage Guides say which reads need `parts`, and the context report counts a read of `rounds`, `moves` or `edits` after the default as a wider read.
