# Rebase replays a Ticket's commits onto its target and keeps one merge commit per landing; the Factory force-pushes only its own branches

Under [Land per Spec](0028-under-land-per-spec-a-specs-work-gathers-on-a-spec-branch-and-lands-together-and-blockers-within-the-spec-clear-on-accept.md) the Factory merges each accepted Ticket's branch into its Spec Branch, and a Spec Branch that conflicts with the base gets the base merged into it. A Spec Branch with many Tickets ends up with a merge per Ticket and merges from the base, which is hard to read and to bisect. Rebase is a Landing option, "Rebase instead of merging", off by default, under which the Factory replays instead of merging.

**Semi-linear history.** With Rebase on, the Factory replays an accepted Ticket's own commits onto its Spec Branch's tip, keeping each one's author, author date and message, and fast-forwards the Spec Branch, so the Spec Branch is linear. When the Spec lands it rebases the Spec Branch onto the base tip, then still makes the one `Merge spec <id>` commit, base tip first and Spec Branch second. With Land per Spec off it rebases the Ticket's branch onto the base and keeps its `Merge <id>` commit. So the base keeps one merge commit per landing, which names what landed and is the landed commit, and everything between merges is linear. The Factory moves the Ticket's own branch to its replayed commits, as `git rebase` does, so the existing ancestry tests (already merged, landed, Changed Repositories) hold with no new record.

**One Project-wide setting, read at each step.** Rebase is stored on the Project's Landing beside Land per Spec, kept whatever the method, and applies under Merge and Pull Request by each Repository's Landing Policy (OffersRebase, RebaseInForce); under Branch it has no effect. An Own Landing doesn't set it: Land per Spec, which it sits beside, is Project-wide too. Each landing step reads it when it runs, and commits already on a Spec Branch are never rewritten to match a change, except by the rebase onto the base at landing, which remakes an older `Merge <id>` commit as a merge.

**The fork point is a Factory-private ref.** What to replay is the Ticket's commits since the Spec Branch tip it was cut from. The Factory records that tip as `refs/code-central/fork/<ticket id>` in each Repository's clone when it cuts the branch, moves it when it moves the branch, and deletes it with the branch. It uses the later of that ref and the merge base of the Ticket's head and the Spec Branch: the ref covers a Spec Branch rewritten since the cut, the merge base an agent who rebased onto the current Spec Branch. Losing the ref falls back to the merge base, which at worst shows up as a conflict for the agent, never as duplicated work.

**`--force-with-lease` only on the Factory's own branches.** Under Pull Request a rebased Spec Branch or Ticket branch no longer descends from what was pushed, so the Factory pushes it with `--force-with-lease=<branch>:<its remote-tracking tip>`. The push helper takes an explicit force flag that only the Spec Branch push and the Ticket branch push may set, and it refuses force for a Repository's base. A base is never force-pushed. The Factory rebases only when it is about to push, not on every base move, so CI doesn't rerun each time.

Conflicts are still checked in every Repository before any is written ([ADR 0049](0049-check-every-repository-before-landing-any-no-all-or-nothing-landing-across-repositories.md)). A conflicting Ticket goes back to Ready with a prompt to rebase; a conflicting Spec Branch opens the [Spec merge Ticket](0038-code-central-opens-spec-merge-tickets-itself-at-the-factorys-request-and-marks-them.md) titled "Rebase the Spec Branch of <spec id> onto the base", which its stored mark, not its title, makes a Spec merge Ticket.

## Considered Options

- **Fully linear history: fast-forward the base to the rebased Spec Branch.** Rejected: the base would lose the one commit that says what landed and when, which the landed commit, Push and the CI gate rest on, and a revert of a Spec would mean reverting each of its commits.
- **Squash each Ticket, or each Spec, into one commit.** Rejected: it throws away the agent's commits and their messages, and a squashed Ticket's branch no longer shares history with what landed, so every ancestry test would need a new record.
- **A per-Repository setting in each Own Landing.** Rejected by the Spec's Round 1: Land per Spec, which Rebase sits beside, is Project-wide, and one Spec's Branches in several Repositories should be built the same way.
- **Read the setting once per Spec, when its Spec Branch is cut.** Rejected: it needs a stored record per Spec, and the human expects a change to take effect from the next step.
- **Work out the fork point from the merge base alone.** Rejected: after the Spec Branch is rewritten under a Ticket, the merge base is older than the cut, and the replay would carry Spec commits that are already there.
- **Force-push with plain `--force`, or allow it on any branch.** Rejected: plain force can overwrite a push the Factory didn't see, and a base holds the human's and other people's work.

## Consequences

`set_landing_method` gains an optional `rebase`, left out to keep the stored value; the landing view shows `rebase` and each Landing Method's capabilities `offers_rebase`, so Project Options enables the checkbox from Go's rule ([ADR 0063](0063-the-ui-reads-derived-rules-from-gos-views-and-only-formats-them.md)). Under Pull Request a rebased branch's pull request shows a force-push, and CI runs on the old tip no longer count. How the host merges the pull request stays the human's choice.
